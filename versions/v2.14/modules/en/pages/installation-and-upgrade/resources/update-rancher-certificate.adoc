Follow these steps to rotate an SSL certificate used by Rancher {xref-install-rancher}[installed on a Kubernetes cluster], when providing your own certificate with `ingress.tls.source=secret`.

The exact steps followed depend on whether the certificate is signed by a private or public CA, and on the configured `agent-tls-mode` setting. More information on this setting can be found in the {xref-tls-settings}#_agent_tls_enforcement[Agent TLS Enforcement] documentation.

In the specific case that Rancher is configured with `agent-tls-mode=system-store` and the Rancher certificate is signed by a public CA, follow the steps in the section <<_agent_tls_mode_system_store_and_a_rancher_certificate_signed_by_a_public_ca,`agent-tls-mode=system-store` and a Rancher certificate signed by a Public CA>>.

For all other cases, i.e. when the Rancher certificate is signed by a private CA or Rancher is configured with `agent-tls-mode=strict`, follow the steps in the section <<_agent_tls_mode_strict_or_a_rancher_certificate_signed_by_a_private_ca,`agent-tls-mode=strict` or a Rancher certificate signed by a Private CA>>.

A summary of the steps is as follows:

. Create or update the `tls-rancher-ingress` Kubernetes secret object with the new certificate and private key.
. Create, update or delete the `tls-ca` Kubernetes secret.
. Reconfigure the Rancher Deployment.
. Reconfigure the cattle-cluster-agent.

[#_agent_tls_mode_strict_or_a_rancher_certificate_signed_by_a_private_ca]
== `agent-tls-mode=strict` or a Rancher certificate signed by a Private CA

Follow these steps if Rancher is configured with `agent-tls-mode=strict`, or if Rancher is configured with `agent-tls-mode=system-store` and the Rancher certificate is signed by a private CA.

[#_1_create_update_the_certificate_secret_object]
=== 1. Create or update the `tls-rancher-ingress` certificate secret object

[NOTE]
====
If switching the certificate source from Let's Encrypt (`ingress.tls.source=letsEncrypt`), first delete the `tls-rancher-ingress` `Certificate` resource in the `cattle-system` namespace before creating or updating the `tls-rancher-ingress` secret. Otherwise, cert-manager will continue reconciling the secret and overwrite the change.

[,bash]
----
kubectl -n cattle-system delete certificate tls-rancher-ingress
----
====

Concatenate the server certificate followed by any intermediate certificate(s) to a file named `tls.crt` and provide the corresponding certificate key in a file named `tls.key`.

Use the following command to create or update the `tls-rancher-ingress` secret object in the Rancher (local) management cluster:

[,bash]
----
kubectl -n cattle-system create secret tls tls-rancher-ingress \
  --cert=tls.crt \
  --key=tls.key \
  --dry-run --save-config -o yaml | kubectl apply -f -
----

[#_2_create_update_delete_the_ca_certificate_secret_object]
=== 2. Create or update the `tls-ca` CA certificate secret object

Copy the CA certificate chain used to validate the Rancher server certificate into a file named `cacerts.pem`, then create or update the `tls-ca` secret in the `cattle-system` namespace.

If the certificate is signed by an intermediate CA, the `cacerts.pem` file must contain both the intermediate and root CA certificates (in this order).

Use the following command to create or update the `tls-ca` secret in the Rancher (local) management cluster:

[,bash]
----
kubectl -n cattle-system create secret generic tls-ca \
  --from-file=cacerts.pem \
  --dry-run --save-config -o yaml | kubectl apply -f -
----

[#_3_reconfigure_the_rancher_deployment]
=== 3. Reconfigure the Rancher deployment

The method used to reconfigure Rancher depends on whether the `ingress.tls.source=secret` and `privateCA: true` values are already set in the running Rancher deployment. If you are changing the certificate source, or passing in the `tls-ca` secret for the first time, these values will need to be updated. You can check the existing Rancher Helm chart values with `helm -n cattle-system get values rancher`.
[loweralpha]
. If the `ingress.tls.source=secret` and `privateCA: true` values are already set, follow the steps in <<_3a_redeploy_the_rancher_pods,3a. Redeploy the Rancher pods>>.
. If either the `ingress.tls.source=secret` or `privateCA: true` values are not set and need to be updated, follow the steps in <<_3b_update_the_helm_values_for_rancher,3b. Update the Helm values for Rancher>>.

Note that the Rancher Helm chart value `privateCA: true` does not indicate that the Rancher certificate was signed by a private CA. This value determines if the `tls-ca` secret is mounted into the Rancher deployment and is used by downstream cattle-cluster-agents to verify the CA of the Rancher certificate. When {xref-tls-settings}#_agent_tls_enforcement[`agent-tls-mode`] is set to `strict`, the agents will enforce verification of the CA, even if the Rancher certificate is signed by a public CA.

[#_3a_redeploy_the_rancher_pods]
==== 3a. Redeploy the Rancher pods

This step is required when the `ingress.tls.source=secret` and `privateCA: true` values are already set and the CA certificate is being updated.

In this scenario a redeploy of the Rancher pods is needed, because the `tls-ca` secret is read by the Rancher pods when starting.

The command below can be used to redeploy the Rancher pods:

[,bash]
----
kubectl rollout restart deploy/rancher -n cattle-system
----

Wait for the Rancher deployment rollout to complete successfully before proceeding:

[,bash]
----
kubectl rollout status deployment/rancher -n cattle-system
----

When the rollout is completed, navigate to `\https://<rancher_server_url>/v3/settings/cacerts` to verify that the value matches the CA certificate written in the `tls-ca` secret earlier. The CA `cacerts` value may not update until all of the redeployed Rancher pods start, which is why it is important to wait for the rollout to complete successfully.

[#_3b_update_the_helm_values_for_rancher]
==== 3b. Update the Helm values for Rancher

This step is required if the certificate source is changing (i.e. from `ingress.tls.source=rancher` or `ingress.tls.source=letsEncrypt`) or if Rancher was previously deployed without `privateCA: true` set.

The below steps update the Helm values for the Rancher chart, so the Rancher pods and ingress are reconfigured to use the new certificate (`tls-rancher-ingress`) and CA (`tls-ca`) created in <<_1_create_update_the_certificate_secret_object,Step 1>> and <<_2_create_update_de_the_ca_secret_object,Step 2>>.

. Retrieve the currently deployed Rancher Helm values and write them to the file `values.yaml`:
+
[,bash]
----
helm get values rancher -n cattle-system -o yaml > values.yaml
----

. Retrieve the version string of the currently deployed Rancher chart to use below:
+
[,bash]
----
helm ls -n cattle-system
----

. Update the Helm values in the `values.yaml` file to include:
+
[,yaml]
----
ingress:
  tls:
    source: secret
privateCA: true
----
+

. Upgrade the Helm application instance using the `values.yaml` file and the current chart version. The version must match to prevent an upgrade of Rancher.
+
[,bash,subs="attributes+"]
----
helm upgrade rancher {rancher-helm-repo}/rancher \
  --namespace cattle-system \
  -f values.yaml \
  --version <DEPLOYED_RANCHER_VERSION>
----

[NOTE]
====
When switching between `ingress.tls.source=letsEncrypt` and `ingress.tls.source=secret` with `privateCA: true` set, restart the Rancher pods after the Helm upgrade. In this scenario, the Helm update alone does not restart the Rancher deployment to pick up the updated `tls-ca` secret.

[,bash]
----
kubectl rollout restart deploy/rancher -n cattle-system
----
====

Wait for the Rancher deployment rollout to complete successfully before proceeding:

[,bash]
----
kubectl rollout status deployment/rancher -n cattle-system
----

When the rollout is completed, navigate to `\https://<rancher_server_url>/v3/settings/cacerts` to verify that the value matches the CA certificate written in the `tls-ca` secret earlier. The CA `cacerts` value may not update until all of the redeployed Rancher pods start, which is why it is important to wait for the rollout to complete successfully.

[#_4_reconfigure_cattle_cluster_agents_to_trust_the_ca]
=== 4. Reconfigure the cattle-cluster-agent in downstream clusters for the updated CA certificate

The cattle-cluster-agent in downstream clusters uses the `CATTLE_CA_CHECKSUM` environment variable to verify the integrity of the CA certificate it receives from the Rancher server.

If the CA certificate used by the Rancher server changes, the `CATTLE_CA_CHECKSUM` environment variable in the cattle-cluster-agent must therefore be updated to match the checksum of the new CA certificate.

. First, generate the new checksum value like so, from a host that can reach the Rancher server (replace `<RANCHER_SERVER_URL>` with the Rancher server URL, e.g. https://rancher.example.com):
+
[,bash]
----
curl -k -s -fL <RANCHER_SERVER_URL>/v3/settings/cacerts | jq -r .value | sha256sum | awk '{print $1}'
----

. Update the `CATTLE_CA_CHECKSUM` environment variable for the cattle-cluster-agent deployment in the downstream cluster with the new checksum value. Replace `<CHECKSUM_VALUE>` with the value generated in the previous step.
+
For Rancher-provisioned RKE2 and K3s clusters with the {xref-kubeconfig-file}[Authorized Cluster Endpoint (ACE)] enabled, the ACE context can be used to connect directly to the downstream cluster. Alternatively, refer to the https://docs.rke2.io/cluster_access[RKE2 Cluster Access] or https://docs.k3s.io/cluster_access[K3s Cluster Access] documentation for instructions on connecting to the downstream cluster using `kubectl` from a controlplane node in the downstream cluster.

+
[,bash]
----
kubectl set env deployment/cattle-cluster-agent -n cattle-system CATTLE_CA_CHECKSUM="<CHECKSUM_VALUE>"
----

[#_agent_tls_mode_system_store_and_a_rancher_certificate_signed_by_a_public_ca]
== `agent-tls-mode=system-store` and a Rancher certificate signed by a Public CA

Follow these steps if Rancher is configured with `agent-tls-mode=system-store` and the Rancher certificate is signed by a Public CA.

[#_1_create_update_the_certificate_secret_object_1]
=== 1. Create or update the `tls-rancher-ingress` certificate secret object

[NOTE]
====
If switching the certificate source from Let's Encrypt (`ingress.tls.source=letsEncrypt`), first delete the `tls-rancher-ingress` `Certificate` resource in the `cattle-system` namespace before creating or updating the `tls-rancher-ingress` secret. Otherwise, cert-manager will continue reconciling the secret and overwrite the change.

[,bash]
----
kubectl -n cattle-system delete certificate tls-rancher-ingress
----
====

Concatenate the server certificate followed by any intermediate certificate(s) to a file named `tls.crt` and provide the corresponding certificate key in a file named `tls.key`.

Use the following command to create or update the `tls-rancher-ingress` secret object in the Rancher (local) management cluster:

[,bash]
----
kubectl -n cattle-system create secret tls tls-rancher-ingress \
  --cert=tls.crt \
  --key=tls.key \
  --dry-run --save-config -o yaml | kubectl apply -f -
----

[#_2_delete_the_ca_certificate_secret_object]
=== 2. Delete the `tls-ca` CA certificate secret object

When Rancher {xref-tls-settings}#_agent_tls_enforcement[`agent-tls-mode`] is set to `system-store` and the Rancher certificate is signed by a public CA, the `tls-ca` secret is not required. If it already exists (for example, from a previous private CA or `agent-tls-mode=strict` configuration), delete it.

First, save a copy of the existing `tls-ca` secret in the Rancher (local) management cluster:

[,bash]
----
kubectl -n cattle-system get secret tls-ca -o yaml > tls-ca.yaml
----

Then proceed to delete the existing `tls-ca` secret from the Rancher (local) management cluster:

[,bash]
----
kubectl -n cattle-system delete secret tls-ca
----

[#_3_reconfigure_the_rancher_deployment_1]
=== 3. Reconfigure the Rancher deployment

This step is required if the certificate source is changing (i.e. from `ingress.tls.source=rancher` or `ingress.tls.source=letsEncrypt`) or if Rancher was previously configured with the value `privateCA: true`. You can check the existing Rancher Helm chart values with `helm -n cattle-system get values rancher`.

Please note that the Rancher Helm chart value `privateCA: true` does not indicate that the Rancher certificate was signed by a private CA. This value determines if the `tls-ca` secret is mounted into the Rancher deployment and is then used by downstream cluster agents to verify the CA of the Rancher certificate. This is used both in the instance that the Rancher certificate was signed by a private CA, but is also used by agents to verify the Rancher CA - even a public one - when {xref-tls-settings}#_agent_tls_enforcement[`agent-tls-mode`] is set to `strict`.

. Retrieve the currently deployed Rancher Helm values and write them to the file `values.yaml`:
+
[,bash]
----
helm get values rancher -n cattle-system -o yaml > values.yaml
----

. Retrieve the version string of the currently deployed Rancher chart to use below:
+
[,bash]
----
helm ls -n cattle-system
----

. Update the Helm values in the `values.yaml` file:
.. As a private CA is not being used, remove the `privateCA: true` field, if present, or set it to `false`.
.. Set the `ingress.tls.source` field to `secret`.
+
[,yaml]
----
ingress:
  tls:
    source: secret
----
+

. Upgrade the Helm application instance using the `values.yaml` file and the current chart version. The version must match to prevent an upgrade of Rancher.
+
[,bash,subs="attributes+"]
----
helm upgrade rancher {rancher-helm-repo}/rancher \
  --namespace cattle-system \
  -f values.yaml \
  --version <DEPLOYED_RANCHER_VERSION>
----

. Wait for the Rancher deployment rollout to complete successfully before proceeding:
+
[,bash]
----
kubectl rollout status deployment/rancher -n cattle-system
----

[#_4_clear_the_cattle-cluster-agent_cattle_ca_checksum_environment_variable]
=== 4. Clear the cattle-cluster-agent CATTLE_CA_CHECKSUM environment variable

When Rancher is configured with {xref-tls-settings}#_agent_tls_enforcement[`agent-tls-mode=system-store`] and a public CA certificate, the `CATTLE_CA_CHECKSUM` environment variable on downstream cluster agents should be set to `""` (an empty string).

For Rancher-provisioned RKE2 and K3s clusters with the {xref-kubeconfig-file}[Authorized Cluster Endpoint (ACE)] enabled, the ACE context can be used to connect directly to the downstream cluster. Alternatively, refer to the https://docs.rke2.io/cluster_access[RKE2 Cluster Access] or https://docs.k3s.io/cluster_access[K3s Cluster Access] documentation for instructions on connecting to the downstream cluster using `kubectl` from a controlplane node in the downstream cluster.

[,bash]
----
kubectl set env deployment/cattle-cluster-agent -n cattle-system CATTLE_CA_CHECKSUM=""
----

[#_5_force_update_fleet_product_name_clusters_to_reconnect_the_fleet_agent_to_rancher]
=== 5. Force Update {fleet-product-name} clusters to reconnect the fleet-agent to Rancher

Select 'Force Update' for the clusters within the {xref-fleet-overview}#_accessing_fleet_in_the_rancher_ui[Continuous Delivery] view of the Rancher UI to allow the fleet-agent in downstream clusters to successfully connect to Rancher.

[#_why_is_this_step_required_1]
==== Why is this step required?

Fleet agents in Rancher managed clusters store a kubeconfig that is used to connect to Rancher. The kubeconfig contains a `certificate-authority-data` field containing the CA for the certificate used by Rancher. When changing the CA, this block needs to be updated to allow the fleet-agent to trust the certificate used by Rancher.

When the CA certificate for Rancher is updated, the fleet-agent in downstream clusters may no longer trust the Rancher server's certificate. Forcing an update of the clusters ensures that the fleet-agent reconnects to Rancher using the updated CA certificate.
